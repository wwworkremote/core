# Interview prep

A **prep pack** is one regenerable markdown briefing per `(candidate, posting)` —
role setup, domain primer, story arc, company hooks, referral play, likely
questions, questions to ask, night-before checklist. It is generated by
`LLM::InterviewPrepGenerator` and rendered in the job posting's Interview Notes
section.

It ships in **two versions, same content**:

| Version | Column | Use |
|---|---|---|
| Human | `interview_prep_pack` | read on screen; the default render |
| Read-aloud | `interview_prep_pack_spoken` | fed to text-to-speech; a `SpokenRewriter` pass, opens with a YAML frontmatter block (title, pronunciation map, sections, spoken minutes), follows [`docs/research/tts-readable-documentation.md`](../../../docs/research/tts-readable-documentation.md) |

Hand [`docs/tts-transform-prompt.md`](../../../docs/tts-transform-prompt.md) to whatever
tool turns the read-aloud version into speech, captions, or a lyrics transcript.

The generator runs on a local model. Its structure is reliable; its **content is a
scaffold, not a finished briefing** — the domain primer comes out shallow, mixes
Mike's own stack into "useful context", confuses skill gaps with domain blind
spots, and sometimes cites a resource that does not exist. This skill's job is to
close that gap: generate, then audit and ground it against real sources before
handing it over.

> [!IMPORTANT]
> The quality bar is [`docs/research/interview-prep-basis-dsp.md`](../../../docs/research/interview-prep-basis-dsp.md) —
> a hand-written prep pack for one real posting. Part 1 is what "good" looks like;
> Part 2 is the per-section spec. Every generated pack is measured against it.

## Steps

### 1. Locate the posting and the interview context

Get the `JobPosting` id (`bin/wwwr postings [filters]`, or the id Mike names). Establish, from Mike:

- [ ] Interview **date and round** (recruiter screen / hiring manager / technical / panel)
- [ ] Any **referral** — is a `Contact` linked to the posting? (`bin/wwwr` has no contact view; check the posting page or a `rails runner`)
- [ ] Anything he already knows that the posting does not say

### 2. Generate the pack

```bash
bin/wwwr interview-prep <job_posting_id> --regenerate
```

Omit `--regenerate` to print what is already stored. Add `--spoken` to print the
read-aloud version instead. `--regenerate` writes both versions.

**Done when:** a pack with all 8 sections exists and you have read it.

### 3. Audit the pack

Dispatch the **`interview-prep-auditor`** subagent with the `job_posting_id`. It
diffs the pack against the quality bar and the posting requirements and returns a
ranked punch list split into **mechanical** (one right answer) and **judgement**
(Mike's call) — without editing anything.

> [!NOTE]
> Run this as a subagent, not inline — the audit reads the full pack, the posting
> body, and the reference doc, and that volume should not land in the main context.

**Done when:** you hold the punch list.

### 4. Ground the domain primer against real sources

Dispatch the **`industry-intelligence-agent`** to verify the primer, giving it the
posting's domain and the primer's claims. It must confirm or correct:

| Check | What to verify |
|---|---|
| Concepts | Are the "MUST know" concepts the ones this domain actually turns on, or generic? What is missing? |
| Acronym citations | Does each acronym resolve to the body that genuinely defines it (IAB Tech Lab, W3C, an RFC, vendor docs)? |
| Learning links | Does each URL resolve, and to the thing claimed? Replace invented links with real ones or a named source. |
| Business model | Is "how it makes money / where the role sits" accurate and current? |

**Done when:** every primer claim is confirmed, corrected, or dropped.

### 5. Pressure-test the sharp sections (optional)

When Mike wants the story and Q&A stress-tested:

- **`career-coach-agent`** — the story arc and positioning against the title/level delta
- **`hiring-manager-agent`** and **`recruiter-agent`** — treat "likely questions" as their own script; do the questions land, what is missing, where is the candidate exposed

### 6. Check the read-aloud version

```bash
bin/wwwr interview-prep <job_posting_id> --spoken | say   # spot check on macOS
```

The `interview-prep-auditor` reports read-aloud defects alongside the content ones.
Confirm: valid frontmatter block, abbreviations and numbers spelled out, no tables,
no bare URLs, no emoji, one idea per sentence. Fix any it flags.

> [!NOTE]
> A regeneration rebuilds the read-aloud version from the corrected human pack.
> If you only hand-edit the human pack, run `--regenerate` (or a scoped
> `SpokenRewriter.call`) so the two stay in sync.

### 7. Fold the fixes in

Apply the mechanical fixes and the confirmed grounding corrections to the pack.
Edit in place — the Interview Notes section has an edit form, or:

```bash
bin/rails runner 'UserJobPosting.find(<id>).update!(interview_prep_pack: <<~MD)
  ...corrected pack...
MD'
```

Leave the **judgement calls** for Mike — do not resolve them.

### 8. Hand off

Give Mike:

- [ ] The sharpened pack (or a pointer to the posting page)
- [ ] The **judgement calls** the auditor surfaced, each with its trade-off
- [ ] One line on what changed from the generated version
- [ ] That the read-aloud version is ready for text-to-speech, with `docs/tts-transform-prompt.md` as the tool instruction

## Known generator failure modes

The auditor checks for these; know them so you can confirm its findings:

- **Stack-as-domain** — "useful context" lists React / Kafka / OpenTelemetry (Mike's tools) instead of domain concepts. Those belong in THE SETUP.
- **Skill-gap-as-blind-spot** — "no React experience" listed under blind spots. A missing tool is THE SETUP's reality check; a blind spot is a domain assumption Mike's background never exposed him to.
- **Invented links** — a plausible-looking URL for a whitepaper or paper that does not exist. Section (e) must name the authority even when it cannot give a real URL.
- **Reality-check overreach** — claiming a hard "no experience" gap the History actually contradicts (Mike has production React and Java).
- **Read-aloud drift** — the local model half-applies the spoken rules: leaves a `[posted band]`, keeps a table, keeps an emoji. Fix by hand or re-run the rewrite.
